# Stockfish Improvements

## Current API

The current `POST /api/stockfish/evaluate` endpoint returns:

```json
{
  "status": "ok",
  "best_move": "d7d5",
  "score": {
    "type": "cp",
    "value": 93
  },
  "depth": 12
}
```

`score.type` is either `cp` for centipawns or `mate` for a forced mate. The score is currently interpreted from the point of view of the side to move.

If Stockfish cannot run, the endpoint returns an explicit unavailable response:

```json
{
  "status": "unavailable",
  "reason": "binary_not_found"
}
```

## UCI Capabilities

Stockfish communicates through the UCI protocol and can receive:

- A position with FEN.
- A starting position with a list of moves.
- A depth limit: `depth`.
- A time limit: `movetime`.
- A node limit: `nodes`.
- A search until mate: `mate`.
- Game-clock limits: `wtime`, `btime`, `winc`, and `binc`.
- A restricted set of candidate moves: `searchmoves`.
- A request for multiple variations with `MultiPV`.

It can return:

- `bestmove`: the best move found.
- `ponder`: the likely reply from the opponent.
- `score cp`: an advantage in centipawns, such as `+42` for approximately `+0.42`.
- `score mate`: a forced mate, such as `mate 3`.
- `wdl`: estimated win, draw, and loss probabilities.
- `pv`: the principal variation.
- `multipv`: the variation number when multiple lines are requested.
- `depth`: the nominal search depth.
- `seldepth`: the deepest search depth reached.
- `nodes`: the number of analyzed positions.
- `nps`: analyzed positions per second.
- `time`: calculation time.
- `hashfull`: transposition-table usage.
- `tbhits`: tablebase consultations.

## Useful Engine Options

- `Threads`: number of CPU threads.
- `Hash`: memory allocated to the transposition table.
- `MultiPV`: number of principal variations returned.
- `UCI_ShowWDL`: enable win/draw/loss estimates.
- `UCI_LimitStrength` and `UCI_Elo`: simulate a target playing strength.
- `Skill Level`: reduce engine strength.
- `UCI_Chess960`: enable Chess960 support.
- `Ponder`: calculate during the opponent's turn.
- `SyzygyPath`: use Syzygy endgame tablebases.

## Product Improvement Ideas

1. Display the three best moves instead of only the first.
2. Show the principal variation as a short continuation.
3. Detect blunders by comparing the evaluation before and after the player's move.
4. Explain that a move loses, for example, `0.8` pawns.
5. Detect tactical opportunities such as mate, piece wins, and direct threats.
6. Display win/draw/loss estimates.
7. Show a confidence indicator based on depth, time, and stability of the evaluation.
8. Add a training mode with progressively stronger hints.
9. Compare the player's move with Stockfish's best move.
10. Use `MultiPV` to explain why one move is better than an alternative.

Stockfish provides calculations, not natural-language explanations, opening names, or pedagogical reasoning. Those elements must be generated by the backend from Stockfish output and the other documented sources.

## Synthese Agentique

L'utilisation de LangChain ou LangGraph ne rend pas automatiquement le produit agentique. Un graphe dont le chemin est entièrement écrit à l'avance reste principalement un workflow déterministe.

Architecture actuelle :

```text
START
  -> validation FEN
  -> identification ouverture
  -> Lichess ou Stockfish selon des règles
  -> RAG
  -> vidéos
  -> synthèse LLM
  -> END
```

La décision critique est actuellement de type :

```python
if in_theory:
    use_lichess()
else:
    use_stockfish()
```

Cette approche est un workflow conditionnel fiable, mais pas un agent autonome avec sélection dynamique d'outils. LangGraph reste utile pour représenter l'état, les branches, les erreurs et les fallbacks. Le LLM peut rester limité à la synthèse afin de garantir la légalité, la traçabilité et la reproductibilité.

La formulation défendable pour une soutenance est :

> Le système est un agent spécialisé, hybride et contraint. Les décisions critiques sont déterministes pour garantir la fiabilité échiquéenne, tandis que le LLM peut raisonner sur les sources, choisir leur pertinence et produire l'explication pédagogique.

## Architecture A: Workflow Deterministe

Les services sont appelés dans un ordre fixe et le code choisit les outils :

```text
FEN
  -> Lichess
  -> Stockfish si sortie de théorie
  -> RAG
  -> LLM de synthèse
```

Avantages :

- Très prévisible.
- Facile à tester.
- Facile à expliquer.
- Temps d'exécution maîtrisable.
- Bon choix pour les décisions de sécurité et la validation des coups.

Limite : le LLM ne choisit pas réellement les outils.

## Architecture B: Collecte Parallele puis LLM Routeur

Les sources sont interrogées en parallèle, puis un seul appel LLM décide quelles informations exploiter :

```text
FEN + question
       |
       +--> Lichess
       +--> Stockfish
       +--> RAG
       +--> vidéos
               |
               v
        LLM routeur et coach
```

Le LLM reçoit un objet structuré :

```json
{
  "question": "Pourquoi Fc4 est-il intéressant ici ?",
  "opening": {
    "name": "Partie italienne",
    "eco": "C50"
  },
  "lichess": {
    "total_games": 54231,
    "moves": [
      {"move": "Bc4", "games": 24000},
      {"move": "Nf3", "games": 18000}
    ]
  },
  "stockfish": {
    "score": 28,
    "principal_variation": ["Bc4", "Nf6", "d3"]
  },
  "rag": [
    {
      "text": "Dans l'Italienne, Fc4 exerce une pression sur f7.",
      "score": 0.84
    }
  ]
}
```

Le LLM peut alors décider que :

- Stockfish est prioritaire pour une question objective ou tactique.
- Lichess est prioritaire pour une question sur les coups fréquents.
- Le RAG est prioritaire pour expliquer une idée stratégique.
- Toutes les sources ne doivent pas forcément être utilisées.

Cette version est plus agentique sans multiplier les appels LLM. Les appels Lichess, Stockfish et RAG peuvent être exécutés en parallèle. Le temps total est alors proche du temps de la source la plus lente, plus un seul appel LLM.

## Architecture C: Tool Calling Dynamique

Le LLM reçoit des outils et décide lui-même lesquels appeler :

```text
Question + FEN
       v
       LLM
       |
       +--> get_lichess_stats(fen)
       +--> evaluate_stockfish(fen)
       +--> search_opening_context(question, eco)
       +--> search_videos(query)
       |
       v
  observations
       |
       +--> nouvelle décision éventuelle
       |
       v
     réponse
```

Exemple :

```text
Utilisateur : Est-ce que ce sacrifice est correct ?
LLM         : appelle Stockfish
Stockfish   : évaluation -2.1
LLM         : cherche le contexte RAG pour expliquer le motif
LLM         : produit la réponse sourcée
```

Avantages : sélection d'outils réellement dynamique et trajectoire non prédéfinie.

Limites : plus lent, plus difficile à tester, plus difficile à contrôler et potentiellement plus coûteux. Cette approche est préférable lorsque les questions utilisateurs sont très variées.

## Architecture D: Routeur de Phase de Jeu

Le LLM peut également déterminer si la position est encore dans l'ouverture, en transition, dans le milieu de jeu ou en finale, sans imposer une règle rigide basée uniquement sur le numéro du coup.

Les signaux fournis au routeur peuvent inclure :

- Numéro du coup.
- Nombre de pièces restantes.
- Présence ou échange des dames.
- Développement des pièces.
- Roques effectués.
- Structure de pions.
- Ouverture identifiée.
- Nombre de parties Lichess comparables.
- Couverture Masters disponible.
- Question de l'utilisateur.

Réponse possible du routeur :

```json
{
  "phase": "opening",
  "confidence": 0.82,
  "reason": "La position reste proche d'une ligne théorique connue.",
  "use_lichess": true,
  "use_stockfish": false,
  "use_rag": true
}
```

Il est préférable de permettre une phase `transition` plutôt que de forcer une classification stricte `opening | middlegame | endgame`.

La couverture Lichess doit rester un signal important : si le routeur identifie une ouverture mais que très peu de parties correspondent à la position, cela indique probablement une sortie de théorie.

## Recommandation pour le POC

Adopter une architecture hybride en deux temps :

```text
1. Validation et collecte déterministes en parallèle
   - python-chess
   - Lichess
   - Stockfish
   - RAG

2. Un seul appel LLM
   - classification sémantique de la demande
   - sélection des sources pertinentes
   - explication pédagogique contrainte par les résultats
```

Les règles déterministes restent obligatoires pour :

- La légalité des coups.
- La validation FEN.
- L'intégrité des scores Stockfish.
- La gestion des timeouts et fallbacks.
- La traçabilité des sources.

Le LLM peut décider :

- Quelle source mettre en avant.
- Si la question porte sur la théorie, la tactique ou la stratégie.
- Si la position semble être en ouverture, en transition ou dans une autre phase.
- Comment adapter l'explication au niveau du joueur.

Cette architecture fournit une agentivité réelle sans adopter immédiatement une boucle ReAct lente et difficile à contrôler.

## Prompt de Routage Possible

```text
Tu es un coach d'échecs et un routeur de sources.

Tu disposes de trois sources :
- Lichess décrit les tendances de jeu et les coups pratiqués.
- Stockfish fournit l'évaluation objective et les variantes tactiques.
- Le RAG fournit le contexte stratégique et pédagogique.

Détermine quelles sources sont pertinentes pour la question.
Ne force pas l'utilisation de toutes les sources.
En cas de désaccord, Stockfish prime pour la correction tactique,
Lichess décrit la pratique et le RAG explique les idées.
Ne présente jamais une information absente des sources comme un fait.
```

## Principes de Performance

- Exécuter les sources indépendantes en parallèle.
- Mettre en cache les réponses Lichess et RAG.
- Limiter Stockfish à une profondeur ou une durée adaptée à la démonstration.
- Limiter le RAG à deux ou trois chunks pertinents.
- Limiter la réponse LLM à quelques centaines de tokens.
- Préférer un seul appel LLM final aux boucles successives lorsque la question est simple.

L'objectif est de conserver une expérience de l'ordre d'une à deux secondes pour une analyse standard, tout en réservant le tool calling itératif aux questions qui nécessitent réellement plusieurs observations.
